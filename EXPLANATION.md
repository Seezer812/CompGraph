# Конспект по проекту компьютерной графики

## 1. Что делает приложение

Проект — оконное приложение C++20 на **DirectX 12**. Оно загружает OBJ-модель Sponza с MTL-материалами и TGA-текстурами, рисует её методом **отложенного освещения** (*deferred shading*) и реализует два задания:

1. Дождь точечных источников света. Источники движутся в сцене, а маленькие эмиссive-шарики показывают их положение.
2. Тесселяция Sponza, displacement mapping и normal mapping. Для крупных поверхностей с картами высоты геометрия дополнительно делится на треугольники, затем смещается по карте высот. Нормали для освещения берутся из normal map.

Главные горячие клавиши:

| Клавиша | Действие |
| --- | --- |
| `W`, `A`, `S`, `D` | движение FPS-камеры по горизонтали |
| `Space`, `Ctrl` | вверх и вниз |
| Правая кнопка мыши | обзор мышью |
| `T` | включить/выключить тесселяцию и displacement |
| `R` | включить/выключить каркасный режим; видны рёбра патчей |
| `Esc` | выход |

Состояние `T` и `R` выводится в заголовок окна.

## 3. Основной кадр: порядок работы

Каждый кадр выполняется функцией `DrawFrame(float dt)` из `SecondSem_CG.cpp`.

1. Ожидается завершение GPU для текущего swap-chain буфера, чтобы CPU не перезаписал занятые ресурсы.
2. `UpdateCamera(dt)` читает клавиши и мышь, обновляет положение и ориентацию камеры.
3. Вычисляется матрица `ViewProj`.
4. G-buffer переводится в состояние render target, очищается и становится текущим framebuffer.
5. `DrawScene(viewProj)` рисует Sponza. Её треугольники подаются как патчи из трёх control points.
6. `DrawRainLightSpheres(viewProj)` рисует маленькие шарики дождя обычным треугольным конвейером.
7. G-buffer переводится в состояние shader resource.
8. `RenderingSystem::DrawLightingPass()` рисует один полноэкранный треугольник и по G-buffer рассчитывает окончательный свет.
9. Back buffer переводится в `PRESENT`, вызывается `Present`, затем GPU получает fence.

### Почему есть fence

CPU и GPU работают параллельно. Если CPU перепишет constant buffer или command allocator, пока GPU ещё читает их, получатся артефакты или ошибка. `ID3D12Fence` сообщает, до какого номера команд GPU уже дошёл. В приложении используются два back buffer (`kFrameCount = 2`), поэтому CPU ждёт только тот буфер, который сейчас будет использовать повторно.

## 4. Координаты, матрицы и камера

### Мировое преобразование Sponza

OBJ импортируется в собственных единицах. Для сцены применяется:

```text
World = Scaling(0.01, 0.01, 0.01) · RotationX(π)
```

Масштаб `0.01` приводит большую исходную Sponza к удобному размеру. Поворот на `π` вокруг X меняет знак координат Y и Z. Это важно для дождя: визуальное направление «вниз» в этой сцене соответствует **росту** мирового `Y`, а не уменьшению.

### View и Projection

Камера хранит:

- `g_camPos` — позицию `E`;
- `g_camYaw` — поворот вокруг вертикали;
- `g_camPitch` — наклон вверх/вниз.

Направление взгляда:

```text
F = normalize(
    sin(yaw) · cos(pitch),
    sin(pitch),
    cos(yaw) · cos(pitch))
```

`XMMatrixLookToLH(E, F, Up)` строит леворукую view-матрицу. `XMMatrixPerspectiveFovLH` строит перспективную матрицу с полем зрения `π/4`, отношением сторон окна и диапазоном глубины `0.1…500`.

Итоговая матрица:

```text
ViewProj = View · Projection
clipPosition = worldPosition · ViewProj
```

В HLSL в матрицах используется `row_major`, потому что C++/DirectXMath и шейдер умножают векторы слева: `mul(vector, matrix)`.

## 5. Constant buffers и выравнивание

### `FrameCB`

Передаётся в `b0`:

- `World` — преобразование объекта;
- `ViewProj` — преобразование в clip space;
- `TimeCamPos` — время и позиция камеры;
- `UvAnimAndPad.xy` — скорость UV-анимации;
- `UvAnimAndPad.z` — глобальный флаг тесселяции (`1` — включена, `0` — выключена клавишей `T`).

### `MatCBGPU`

Передаётся в `b1` для каждого подмеша. Содержит цвет `Kd`, спекулярные параметры, UV-параметры и флаги наличия карт:

- `HasNormalMap`;
- `HasDisplacementMap`;
- `EnableTessellation`;
- `IsEmissive` — материал шариков дождя.

В DirectX 12 адрес constant buffer обязан быть кратен 256 байтам. Поэтому обе C++ структуры объявлены как `alignas(256)`, а данные материалов раскладываются с шагом `kCbAlign = 256`.

## 6. Загрузка OBJ, MTL и текстур

`ObjLoader` читает OBJ и формирует:

- массив `MeshVertex`: position, normal, UV;
- общий index buffer;
- `Submesh`: диапазон индексов и индекс материала;
- `Material`: `Kd`, `Ks`, `Ns`, пути diffuse/specular карт, UV scale/offset.

Каждый материал получает четыре последовательных SRV в descriptor heap:

| Регистр шейдера | Карта |
| --- | --- |
| `t0` | albedo/diffuse |
| `t1` | specular |
| `t2` | normal |
| `t3` | displacement |

Normal и displacement не записаны стандартными полями MTL, поэтому путь выводится из имени diffuse-карты. Например:

```text
sponza_floor_a_diff.tga
→ sponza_floor_a_ddn.tga
→ sponza_floor_a_diff_displacement.tga
```

Если normal map отсутствует, в `t2` ставится плоская нормаль `(0.5, 0.5, 1.0)`. Если displacement-карты нет, ставится белая карта, но флаг `HasDisplacementMap` выключен, поэтому смещения не будет.

## 7. Deferred shading и G-buffer

### Идея

При forward rendering каждая модель рассчитывает освещение от каждого света. Это неудобно при десятках или сотнях источников. В deferred shading сначала записываются свойства поверхности для каждого экранного пикселя, а свет рассчитывается вторым проходом.

### Три render target-текстуры

`GBuffer` создаёт три текстуры:

| G-buffer | Формат | Содержимое |
| --- | --- | --- |
| albedo | `R8G8B8A8_UNORM` | базовый цвет |
| normal | `R16G16B16A16_FLOAT` | мировая нормаль; alpha используется как признак эмиссии |
| position | `R16G16B16A16_FLOAT` | мировая позиция |

После геометрического прохода ресурсы переходят из `D3D12_RESOURCE_STATE_RENDER_TARGET` в `D3D12_RESOURCE_STATE_PIXEL_SHADER_RESOURCE`. Такие переходы обязательны в D3D12: API не угадывает, как ресурс будет использован дальше.

### Geometry Pixel Shader

`GeometryPS` записывает в G-buffer:

```text
albedo   = Albedo(uv) · Kd
normal   = normalW
position = positionW
```

Для эмиссive-шариков alpha normal-buffer содержит `1`. В lighting pass это добавляет постоянный яркий вклад, поэтому шарик виден, даже если на него не попадает свет.

## 8. Normal mapping

Normal map хранит нормаль в **tangent space**. Значения текстуры лежат в `[0, 1]`, поэтому сначала выполняется распаковка:

```text
nT = 2 · NormalMap(uv) - 1
```

Нужен базис TBN:

- `N` — нормаль поверхности в мировом пространстве;
- `T` — касательная (tangent);
- `B` — бинормаль/bitangent.

В проекте `T` вычисляется в пиксельном шейдере по производным:

```text
dp1 = ddx(P),   dp2 = ddy(P)
duv1 = ddx(uv), duv2 = ddy(uv)
T = normalize(dp1 · duv2.y - dp2 · duv1.y)
B = normalize(cross(N, T))
```

После этого нормаль карты переводится в мир:

```text
nW = normalize(T · nT.x + B · nT.y + N · nT.z)
```

Эта `nW` записывается в G-buffer и используется во всех расчётах освещения. Normal map меняет только направление нормали и внешний вид освещения, но не меняет силуэт модели.

## 9. Тесселяция

### Зачем она нужна

Displacement действительно меняет вершины. Если у исходного треугольника мало вершин, карта высот не может показать мелкий рельеф. Тесселяция добавляет вершины на GPU перед rasterization.

### Конвейер

```text
Vertex Shader → Hull Shader → Tessellator → Domain Shader → Pixel Shader
```

1. **Vertex Shader (`GeometryVS`)** переводит вершины в мировое пространство.
2. **Hull Shader (`TessellationHS`)** выдаёт control points без изменения.
3. **Patch constant function (`TessellationFactors`)** задаёт количество разбиений патча.
4. Встроенный fixed-function tessellator создаёт новые точки.
5. **Domain Shader (`TessellationDS`)** интерполирует атрибуты новых точек и смещает их по height map.
6. Pixel Shader заполняет G-buffer.

Один исходный треугольник подаётся как `D3D_PRIMITIVE_TOPOLOGY_3_CONTROL_POINT_PATCHLIST`, то есть как патч с тремя control points.

### Hull Shader и уровни тесселяции

Для треугольного патча задаются три коэффициента на внешних рёбрах и один внутри:

```hlsl
float edges[3] : SV_TessFactor;
float inside   : SV_InsideTessFactor;
```

В `TessellationFactors` вычисляется центр патча `C` и расстояние до камеры:

```text
d = |C - cameraPosition|
t = lerp(6, 1, saturate(d / 20))
```

То есть до расстояния 0 уровень равен 6; на расстоянии 20 и дальше — 1. `saturate(x)` ограничивает `x` диапазоном `[0, 1]`.

Текущая реализация задаёт одинаковый уровень для трёх рёбер и внутренности. Это простой способ избежать щелей между соседними патчами одного материала. Используется `fractional_odd`: уровень меняется более плавно при движении камеры.

При `T = off`, отсутствии displacement map или выключенном флаге материала все уровни равны 1: исходный треугольник не делится.

### Какие материалы тесселируются

Тесселяция включена для крупных жёстких частей Sponza: `floor`, `bricks`, `arch`, `ceiling`, `column_a`, `column_b`, `column_c`, `details`, `roof`, `thorn`.

Для ткани, цепей, листьев и ваз она выключена. Причина: их тонкая геометрия может некорректно деформироваться, а тесселяция на всех 3D-мешах Sponza была бы слишком дорогой.

### Domain Shader и displacement

Tessellator передаёт barycentric coordinates `(b0, b1, b2)`, где:

```text
b0 + b1 + b2 = 1
```

Для любого атрибута `A` внутри треугольника используется интерполяция:

```text
A = b0·A0 + b1·A1 + b2·A2
```

Так интерполируются позиция, нормаль и UV. Высота берётся из красного канала карты:

```text
h = DisplacementMap(uv).r
P' = P + N · ((h - 0.5) · 0.10)
```

`h - 0.5` центрирует высоту: `0.5` не двигает поверхность, меньшие значения уводят её против нормали, большие — по нормали. `0.10` — фиксированная сила displacement в мировых единицах.

В отличие от normal mapping, displacement меняет истинную мировую позицию `P'`, depth buffer и силуэт объекта.

## 10. Освещение

`LightingPS` — полноэкранный pixel shader. Он читает `albedo`, `N` и `P` из G-buffer. В сцене есть направленный свет, точечный свет, spotlight камеры и динамические точки дождя.

### Направленный свет

Для него направление одинаково в любой точке:

```text
L = normalize(-lightDirection)
```

### Точечный свет и затухание

Для точки света `S`:

```text
toLight = S - P
dist = |toLight|
L = toLight / dist
t = 1 - saturate(dist / range)
attenuation = t²
```

За пределами `range` источник пропускается. Квадрат делает спад света мягче около границы.

### Spotlight

Помимо затухания по расстоянию вычисляется угол:

```text
ρ = dot(-L, axis)
spot = saturate((ρ - cosOuter) / (cosInner - cosOuter))
attenuation *= spot²
```

`cosOuter` определяет внешний конус, `cosInner` — полностью освещённую центральную часть.

### Diffuse и specular

Диффузная часть Ламберта:

```text
diff = max(0, dot(N, L))
```

Для блика используется half-vector:

```text
V = normalize(cameraPosition - P)
H = normalize(L + V)
spec = max(0, dot(N, H))^48 · 0.28
```

Итоговый вклад:

```text
(albedo · diff + spec) · lightColor · intensity · attenuation
```

## 11. Дождь источников света

### Данные

`RenderingSystem::RainLight` хранит позицию и скорость падения. Максимум — 125 дождевых источников плюс 3 штатных, всего не более 128 источников в constant buffer.

### Симуляция

`UpdateLightRain(dt)`:

1. При первом вызове создаёт 100 капель на различных высотах — требование «не менее 100 до исчезновения» выполняется сразу.
2. Затем порождает 18 капель в секунду.
3. После заполнения пула новая капля удаляет самую старую.
4. В текущей системе координат Sponza капля движется с ростом мирового `Y` до фиксированного уровня пола.

Это простая кинематическая модель:

```text
y(t + dt) = min(yFloor, y(t) + speed · dt)
```

Важно: сейчас уровень пола задан константой. Точная физическая коллизия с каждым треугольником Sponza ещё не реализована; для неё нужна вертикальная ray cast-проверка по геометрии или пространственная сетка треугольников пола.

### Почему дождь не должен тормозить приложение

Наивный lighting shader проверял бы 125 точек для каждого пикселя экрана. Это слишком дорого. Поэтому пространство дождя делится CPU на сетку `6 × 5`; для пикселя проверяются только источники из своей и восьми соседних ячеек. Так число тестов уменьшается примерно с 125 до нескольких десятков на пиксель.

### Шарики капель

`CreateRainSphereResources()` создаёт маленький октаэдр: 6 вершин и 8 треугольников. Для каждой капли рисуется экземпляр с собственной матрицей `World`. Материал имеет `IsEmissive = 1`, поэтому шарик виден как светящийся объект и не зависит от попадания другого света.

Для шариков используется отдельный PSO без Hull/Domain shaders. Это важно: тесселяционный pipeline ждёт патчи по 3 control points, а октаэдр рисуется обычным `TRIANGLELIST`.

## 12. Pipeline State Objects и режим рёбер

Создаются три PSO с одной root signature:

| PSO | Назначение |
| --- | --- |
| `g_pipelineGeo` | Sponza с Hull/Domain shaders, solid fill |
| `g_pipelineGeoWire` | та же Sponza, но `D3D12_FILL_MODE_WIREFRAME` |
| `g_pipelineGeoSimple` | шарики дождя без тесселяции |

Клавиша `R` только выбирает между `g_pipelineGeo` и `g_pipelineGeoWire`. Wireframe показывает реальные рёбра после разбиения, поэтому это удобный способ продемонстрировать преподавателю изменение плотности тесселяции около камеры.

## 13. Термины, которые полезно знать

| Термин | Короткое объяснение |
| --- | --- |
| **PSO** | Pipeline State Object: набор настроек рендеринга и скомпилированных шейдеров |
| **Root signature** | описание того, какие CBV/SRV/sampler ресурсы доступны шейдерам |
| **CBV** | Constant Buffer View — доступ шейдера к небольшому буферу констант |
| **SRV** | Shader Resource View — доступ шейдера к текстуре или буферу для чтения |
| **Descriptor heap** | память дескрипторов SRV/CBV/UAV, видимая GPU |
| **G-buffer** | набор текстур с атрибутами поверхности для deferred shading |
| **Patch** | примитив для tessellator; здесь один треугольник из трёх control points |
| **Hull Shader** | задаёт control points и факторы тесселяции |
| **Domain Shader** | получает точки, созданные tessellator, интерполирует и смещает их |
| **TBN** | tangent-bitangent-normal базис для normal map |
| **Displacement map** | карта, реально перемещающая вершины |
| **Normal map** | карта, меняющая нормали при освещении без изменения геометрии |
| **Barycentric coordinates** | веса трёх вершин треугольника, сумма которых равна 1 |
| **Resource barrier** | явное указание смены назначения GPU-ресурса в D3D12 |

## 14. Типовые вопросы на защите

### Чем normal mapping отличается от displacement mapping?

Normal mapping меняет только нормаль, поэтому влияет на свет и блики, но не меняет глубину, силуэт и контур. Displacement смещает вершины, поэтому меняет реальную геометрию; для детальной карты ему нужна тесселяция.

### Почему displacement выполняется в Domain Shader, а не в Pixel Shader?

Pixel Shader уже работает после rasterization и не может изменить положение вершины или silhouette. Domain Shader вызывается для новых вершин, созданных tessellator, поэтому может изменить `positionW` и `clipPos` до rasterization.

### Почему тесселяция зависит от расстояния до камеры?

Мелкие детали вдали неразличимы, но требуют GPU-времени. Адаптивная тесселяция выделяет больше треугольников там, где зритель увидит рельеф, и меньше там, где это неважно.

### Почему нельзя включить высокий уровень тесселяции для всей Sponza?

Sponza уже содержит много треугольников. Если каждый треугольник разделить, например, в 6 раз по ребру, число растеризуемых треугольников возрастёт примерно пропорционально квадрату уровня. Это быстро станет десятками миллионов треугольников и вызовет падение FPS.

### Зачем нужен G-buffer?

Он отделяет рисование геометрии от расчёта света. Геометрия записывается один раз, затем можно добавлять много источников света без повторной отрисовки всей Sponza для каждого источника.

### Почему размер constant buffer кратен 256 байтам?

Это требование D3D12 для адреса CBV. Выравнивание делает доступ GPU к константам корректным и эффективным.

### Почему в normal mapping нужны T, B и N?

Normal map описывает нормаль относительно поверхности, а не мировых осей. Базис TBN переводит это локальное направление в мировое пространство, где оно можно использовать в `dot(N, L)`.

### Что показывает клавиша `R`?

Каркасный rasterizer mode. При включённой тесселяции он показывает, что один исходный треугольник стал сеткой из множества треугольников; при удалении камеры сетка становится реже.

### Почему у капли есть шарик, если источник света сам по себе существует?

Точечный источник света не является геометрическим объектом: он освещает окружающие поверхности, но сам не обязан быть видимым. Эмиссive-шарик — визуальный маркер позиции источника.

## 15. Что можно улучшить

1. Реализовать точную коллизию дождя с треугольниками пола Sponza, а не фиксированный `Y`.
2. Передавать касательные из OBJ, а не вычислять их в Pixel Shader через `ddx/ddy`.
3. Вычислять edge factors отдельно, используя расстояния до концов ребра; это лучше предотвращает crack между разными материалами.
4. Использовать texture mipmaps для карт высот и выбирать mip level по расстоянию.
5. Ввести PBR-освещение, roughness/metallic карты и environment lighting.
6. Перенести световую сетку дождя в compute shader или использовать tiled/clustered deferred shading.
